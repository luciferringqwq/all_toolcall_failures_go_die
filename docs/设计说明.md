# 所有的工具调用失败都给我tm去死吧插件 · 设计说明

（技术名 `all_toolcall_failures_go_die`，只作为目录/模块/配置路径/服务名使用。）

## 1. 约束

- **只新增插件**：不改 `src/`，不改其它 `plugins/`。
- **fail-open**：任何一步失败都必须让原响应原样通过。
- **省 token**：能本地修就本地修；必须请 LLM 时只发一次、只带最小上下文。

由第一条约束可以推出：唯一允许介入的地方是**事件系统**，唯一允许写回的
字段是框架文档里声明可改的那几个（`message` / `reasoning_content` /
`reasoning_parts` / `tool_calls`）。

## 2. 为什么用 `AFTER_LLM_REQUEST`

框架在 `src/kernel/llm/request_execution.py` 里发布该事件，并把
`message`、`tool_calls`（`list(resp.call_list)`）等字段放进事件参数；
事件返回后会把它们回写到 `LLMResponse`，其中 `tool_calls` 支持
`ToolCall` 对象或 `{"id","name","args"}` 字典两种形态。

这条链路有两个好处：

1. **在 chatter 之前**：chatter 拿到响应后才发现「没有调用」「未知的工具」
   「执行异常」，那时已经晚了（要么放弃发言，要么再请求一次模型）。
2. **有原始文本**：`message` 里保留着模型真正吐出的内容，是修复最关键的证据。

`weight` 取 200，高于 `plain_text_kicker`（100）。事件总线按 weight 降序执行，
所以「先尝试把调用修好」，修不好才轮到纯文本处理插件接手。

## 3. 为什么需要 `BEFORE_LLM_REQUEST` 缓存

`AFTER_LLM_REQUEST` 的参数里**没有** `tools`，但校验「工具名是否合法」
「哪个参数是必填」必须知道这次真正发出去的工具集。所以：

- `BEFORE_LLM_REQUEST` 时把 `params["tools"]` 编译成 `ToolCatalog`，
  键为 `(request_name, stream_id)`；
- `AFTER_LLM_REQUEST` 时按同样的键取回；取不到则退化为「同 request_name
  最近一次」；
- 再取不到就**放弃修复**（`main.catalog_fallback=false`）。只有显式打开该开关
  才会退回全局组件注册表——因为「全局有、本次没提供」的工具被写回后，调度层
  会判「未知的工具」，比不修更糟；
- 缓存带 TTL（300s）与容量上限（128），避免长跑内存增长。

### 这份目录为什么是准的

框架并不是把「工具列表」单独传进事件，而是从 payload 里抽出来的
（`src/kernel/llm/request_execution.py`）：

1. `tools = extract_tools(payloads)`（`:129`）——只收 `ROLE.TOOL` payload 里
   属于 `LLMUsable` 的类或实例（`extract_tools`，`:57-70`）；
2. `BEFORE_LLM_REQUEST` 发布 `"tools": list(tools)`（`:191`）；
3. 同一个列表随后原样交给 `client.create(tools=tools)`（`:214`），provider 适配器
   对每一项调用 `to_schema()`。

也就是说：**我 `to_schema()` 拿到的 schema，和模型看到的 schema 是同一份**，唯一
差异是适配器额外注入的 `reason`（见下一节，已专门处理）。另外 `BEFORE` 位于重试
循环内部（`:176-208`），每次 provider 尝试都会刷新缓存；请求名与 `stream_id` 在
前后两个事件里都取自同一个 `request.meta_data`，所以配对是可靠的。

已知的边角误差（都不影响正确性）：

- `tools` 在上下文裁剪（`prepare_payloads_for_model`）**之前**统计，若某个上下文
  管理器裁掉了 TOOL payload，我这边会「多知道」几个工具（偏宽松）；
- 若某次调用没传 `stream_id`，并发同名请求会共用 `(request_name, "")`；此时若
  工具集不同，理论上可能错配——但同名请求的工具集由同一个 chatter 配置决定，
  实际相同；且未命中时的策略是放弃修复，不会乱写。

## 4. 校验模型

`ToolSpec` 是从 provider schema 里抽出的最小信息：名字、描述、参数
`properties`、必填列表（**剔除 `reason`**）、是否接受 `**kwargs`。

> 为什么剔除 `reason`：框架的 `_to_openai_tool` 会给 provider schema 自动注入
> `reason` 必填参数，而组件自身的 `execute` 并不需要它（不需要时框架会自动
> 剥离）。如果把 `reason` 当作真正的必填项，会把大量正常调用误判为缺参。

`audit_call()` 逐条产出问题，并按「能不能本地解决」分成两类：

| code | 含义 | needs_llm |
| --- | --- | --- |
| `unknown_tool` | 工具名不在目录里 | ✓ |
| `missing_required` | 缺必填参数 | ✓ |
| `missing_args` | 整个 `args` 都缺失 | ✓ |
| `invalid_args` | `args` 无法解析成对象 | ✓ |
| `partial_name` | 名字缺前缀，已本地补全 | ✗ |
| `args_parsed` | args 字符串已解析 | ✗ |
| `coerced` | 标量类型已按 schema 纠正 | ✗ |
| `dropped_args` | 已删除多余参数 | ✗ |
| `reason_added` | 已补 `reason` | ✗ |

判定逻辑非常简单：

- 有 `needs_llm` 的问题 → 必须请 LLM；
- 只有本地问题 → 本地改完写回，`changed=True`；
- 一点问题都没有、也没有本地改动 → 什么都不做（这也是绝大多数请求的路径）。

## 5. 「纯文本」的处理

纯文本有三种情况，处理顺序是「越确定越便宜的先做」：

| 情况 | 处理 | 成本 |
| --- | --- | --- |
| 文本里其实藏着坏掉的调用（半截 JSON、`send_text(...)`） | 本地抢救 | 0 |
| 文本就是一句要给用户的话（「你好，我在」） | 套壳成发送工具调用 | 0（本地）/ 一次极小请求 |
| 都不是 | 不动（或按 `suspicious` 判定后再修） | 0 |

### 5.1 本地抢救

`extract_candidates` 依次尝试 `json.loads` 整体 → 去代码围栏 → 平衡括号切片 →
`ast.parse` 的 `name(k=v)` 调用语法；每个候选都过一遍 `audit_call`，**全部合法**才采用。

### 5.2 套壳（本插件的主路径）

框架里 chatter 只在 `tool_calls` 非空时才执行动作，纯文本会被记一条
「LLM 返回纯文本而非工具调用」然后直接 `Wait`（`neo_default_chatter/session.py`）。
所以「纯文本」本质上等于「消息写好了但没发出去」，套壳就是把它包成
当前 chatter 的发送工具调用。

难点是**工具名不能写死**：不同 chatter 的发送动作名字可能不同
（`send_text` / `reply_message` / ……），同一个目录里还可能有 `send_emoji_meme`
这种「也在发送、但不是文本」的干扰项。识别规则写在 `core/send_tool.py`：

1. `plain_text.send_tool_name` 显式指定；
2. 名字命中 `send_tool_patterns`（glob）且存在正文参数；
3. 唯一的「只有一个必填字符串参数、且参数名属于 `body_params`」的工具；
4. 描述含发送/回复关键词且有正文参数。

命中多个时按 `chatter_allow` 收敛——框架的 `filtering.py` 正是用
`chatter_allow` 按 chatter 过滤可用组件，所以「属于当前 chatter」是可判定的：
请求名（框架默认等于 chatter 名）出现在它的 `chatter_allow` 里即为当前 chatter。
仍然不唯一才交给模型选。

正文参数由 `body_params` 顺序决定（`content` → `text` → `message` → …），
原文**原样**塞进去，不拆句、不改写。

### 5.3 剩下的文本

`suspicious` 模式的启发式（`looks_like_tool_call`）只看「像不像坏掉的调用」：
JSON 结构、`tool_calls`/`function_call`/`arguments` 等关键词、`<tool_call` 标签、
函数调用式语法、提到了本次可用工具名。命中才进 LLM，避免对普通聊天浪费请求。
`wrap` 模式下如果目录里根本没有发送工具，也退回到这条判断。

## 6. 修复请求的形状

修复请求是**全新的、独立的最小上下文**，不携带主对话历史：

```
system: 你是工具调用修复器。只输出一个 JSON。
        {"tool_calls":[{"name":..., "args":{...}}]} 或 {"no_tool_call":true,...}
        name 必须来自给定目录；参数必须符合 schema；不要输出解释。

user:   【可用工具】action-send_text(必填: content)、action-pass_and_wait ...
        【重点工具】action-send_text 的完整 schema（单工具补参时）
        【模型原始输出】<截断后的 message>
        【框架已解析出的调用】[...]
        【框架报错】- 调用 action-send_text 缺少必填参数 content
```

三种请求：

- `plan`：从原始输出重建整批调用（坏调用多、工具名未知时用）。
- `fill_args`：只给一个已知工具补参数，提示词更短（只有一个坏调用时用）。
- `wrap`：纯文本套壳。system 换成「消息发送套壳器」，明确要求「原文一字不改」、
  「不许填正文参数之外的参数」、「没有发送工具就回 `no_tool_call`」；
  user 里额外列出「发送类候选」和「正文参数名候选」，让模型不必自己猜。

回复解析（`parse_repair_reply`）容忍代码围栏；也接受「只给了 args」的偷懒回复
（此时用 `fallback_name` 补齐工具名）。解析不出来的回复一律视为失败。

## 7. 结果回写与二次校验

LLM 的回复**不可信**，所以写回前要再跑一次 `audit_call`：

- 任一候选仍有 `needs_llm` 问题 → 放弃，保持原响应；
- 候选的工具名必须能在目录里解析到 → 否则放弃；
- 全部通过 → 补 `id`、写回 `params["tool_calls"]`。

这条规则保证「修复」永远不会把响应改得更坏。

`message` 的处理：默认**保留**模型原文（`plain_text.clear_message_on_repair=false`），
让它作为 assistant 独白与修好的调用一起进入上下文——chatter 大多依赖 assistant
文本推进对话。怕「半截 JSON」污染上下文时可改为清空。

## 8. 递归与限流

- `skip_request_name_patterns` 默认包含 `toolcall_repair*`，修复请求自己的
  响应不会再被修复；
- 另有 `ContextVar` 守卫，即使配置被改坏也不会自我递归；
- `max_repairs_per_minute` 只统计真正发出去的修复请求（本地修复不计数），
  防止某个模型持续崩坏时不停烧钱。

## 9. 未做的事

- 不重试：一次故障最多修一次，修不好就交给下游（纯文本插件 / 正常错误处理）。
- 不处理流式：该阶段没有 `tool_calls` 可修。
- 不猜测「模型其实想调用什么」：没有证据（原始输出里没有调用痕迹）时不发请求。
- 套壳不拆句：一段纯文本只会变成一次发送调用，不会自作主张拆成多条消息。
- 套壳不伪造工具：目录里没有发送类工具时宁可不动，也不写回本次请求没提供的工具
  （框架会判「未知的工具」，比不修更糟）。
